## 前言

手里有台中兴 SR7100，想给它装个 OpenWrt，顺便把 OpenClash 塞进去。我没做过路由器移植，一开始想得非常朴素：原厂系统也是 Linux，他能驱动这些硬件，我们参考着写一遍不就行了？

而且我还提了一个要求：不想拆设备，希望一次成功。

后来的结果是，设备拆了，串口焊了，USB 串口模块没带还临时拿 ESP32-C3 写了一个。最后甚至把 B 系统的空间拆出来，给 Plugin 扩了个容。

只能说，需求一开始确实是很简单的。

这次是我和 Codex 一起做的。我负责提供机器、焊串口、接线、插拔网口和真正的断电测试；固件分析、驱动适配、构建和测试脚本主要交给它。下面记几个有意思的坑，适配代码放在了 [GitHub](https://github.com/GaoYuCan/sr7100-openwrt)。

## ARM64 不等于随便找个 ARM64 镜像就能启动

原厂 shell 里看一眼：

```text
Linux SR7100 5.4.196 ... aarch64 GNU/Linux
```

CPU 是 ZX279133，双核 Cortex-A53，内存 512 MiB，无线芯片是 MT7992。看起来相当眼熟，至少不是完全没见过的架构。

但是 `aarch64` 只说明 CPU 执行什么指令。中断控制器、时钟、复位、PCIe、NAND 控制器，还有那一坨负责转发数据包的东西，内核不会因为看见 ARM64 就自己猜出来。

最后选定的是 OpenWrt 25.12.5 对应的 Linux 6.12.94。原厂 5.4 的模块当然不能直接往里面塞。好在也不是从一张白纸开始：cnjn 已经做过 ZX279133/SR1010 的主线内核和 ImmortalWrt 适配，这部分参考非常重要。时钟、GPIO、pinctrl、MDIO 等都有东西可以接着研究。E2631 的项目也给了引导调试方面的参考，但它是另一颗 SoC，镜像不能直接拿来刷。

我最开始那句“他能适配我们适配不了”，最后确实变成了适配。不过中间省略的工程量有点多。

## 不拆机计划结束于串口

最开始我有 root shell，还在考虑 kexec。原厂内核里能找到 `machine_kexec`、`kernel_kexec`，看起来可以把新内核直接塞进内存跳过去。

问题是，跳过去之后原来的 Wi-Fi 就没了。新系统如果没有把 PCIe 和无线带起来，远程 shell 也就一起没了。另外原系统跑着的 DMA、看门狗、设备中断怎么交接，也不是“支持 kexec”这一个条件能解决的。

于是我还是把机器拆了，找到串口焊了线。

然后发现没带 USB 串口模块。

手边倒是有个 ESP32-C3-Supermini，那就现写一个吧。用芯片自带的 USB Serial/JTAG 接电脑，另开 UART1，GPIO4 做 TX、GPIO5 做 RX，中间原样转发。测过路由器 TX 的空闲电平约 3.3 V，接 GND 和交叉的 TX/RX，VCC 不接。

第一轮能看到 ESP32 自己的 ROM 日志和桥接程序的 READY，我还以为路由器没输出。其实那只能证明 ESP32 活着，跟路由器串口接没接对完全是两回事。

接对之后终于看到：

```text
SPI NAND
start read bootloader
non secure boot
...
*******************entering csp boot.
*** Press 1 means entering boot mode***
```

我按 `1` 又没效果。这里还有个很蠢但很真实的原因：监视脚本默认是 receive-only，键盘根本没往设备发。

后来给脚本加了一个明确的模式，等到那行提示出现，只发一次 ASCII `1`，自动发送到此为止。进入菜单后才交互，不是从上电开始无脑往串口里灌 `111111`。

Mac 没网口，TFTP 就交给另一台 Linux 电脑。更重要的是，这台电脑的管理连接走手机热点，网线接路由器。这样路由器重启的时候，我和 Codex 不会连测试主机也一起失联。

## PCIe 通了才轮得到无线

MT7992 有 mt76 可以用，这是好消息。但这颗无线芯片通过 PCIe 接在 ZX279133 上，首先得让主控的 PCIe 控制器、PHY、时钟、复位和地址窗口正确工作。

这一段需要对照已有 SoC 适配和厂商初始化流程，不能只在设备树里写一句 `status = "okay"` 就宣布完成。最后真机能枚举到 `14c3:7992`，链路是 Gen3 x2，再把 backports、cfg80211、mac80211、mt76 和 mt7996e 编译到同一个内核基线上。

接着是校准数据。本机读出的 MT7992 EEPROM 是 7680 字节，它不是网上随便下一个默认文件就能替换的东西。适配里专门加了限制：板级 EEPROM 缺失、长度不对或者芯片 ID 不匹配，就停止初始化，不悄悄换成默认模板继续发射。

这里还有一段插曲：最初无线能关联、能 ping，但是信号只有大约 −80 dBm，电脑明明就在旁边。

因为我把天线拆了。

后面先停了无线收发测试，做有线和离线适配，等天线装回去再统一测。最终双频关联、DHCP、双向文件校验和重连都通过了。这个芯片在系统里还是一个 `phy0` 下挂两个 radio index，也不是简单照抄“两块网卡”的配置。

## 网口最坑的是三个口共用一套 DMA

一开始先把单个口跑通。后来按外壳标签一个一个换线，才确认了对应关系：

| 外壳端口 | SMAC | PHY 地址 | PPU 端口 |
| --- | --- | --- | --- |
| WAN | 0 | `0x0a` | 1 |
| LAN1 | 1 | `0x0b` | 2 |
| LAN2 | 2 | `0x0c` | 3 |

但是把单口驱动复制三份不会自动得到三个独立网口。这三个口共用底层 DMA，收到一个描述符之后，得知道包究竟从哪个物理口进来，再交给对应的 netdev。

厂商实现和真机采样对上之后，关键的入口字段是：

```c
unsigned int source = (word1 >> 16) & 0x3f;
```

这台机器对应 `1..3`，再映射到 `SMAC0..2`。不在范围内、接口没有配置、接口已经关闭的包直接拒绝，不能看不懂就扔给 LAN。否则 WAN/LAN 隔离在驱动里就先漏了。

另一个容易忽略的地方是生命周期：

```text
第一个口打开：准备共享硬件和 DMA
其他口打开：增加该口，不重复初始化 DMA
关闭一个口：停该口，其他口继续工作
最后一个口关闭：停止并释放共享 DMA
```

TX 的完成、统计和队列记账也要记得属于哪个端口。排空失败时更不能把还被 DMA 引用的资源直接释放，所以实现里会停住整个共享数据通路，留下故障状态。

还有个相当阴间的区别：**在 U-Boot 菜单里手工启动能联网，直接上电自动启动却不行。**

最后发现原厂自动启动路径会给 PHY 设置 `BMCR_PDOWN`，进入菜单做实验反而绕过了这一步。GEPHY 驱动补了 `genphy_resume`，恢复 PHY 电源状态之后，自动启动才真正和手工测试对齐。

所以“我在串口里敲了命令，它能跑”距离“插上电就能放家里用”，真的还隔着一段路。

## 42 MiB 的启动镜像撞上了 U-Boot

调试的时候，为了方便，整个用户空间都塞在 RAM 启动载荷里，镜像一路长到了大约 42 MiB。我看着原厂那个几 MiB 的内核，就问了一句：原来的不是才不到 8 MiB 吗，怎么搞这么大？

其实比较错对象了。原厂是几 MiB 的内核 FIT，加上另一块接近 29 MiB 的 rootfs。我们把内核、LuCI、Ruby、OpenClash、Mihomo 等一起塞到了一个启动包里。

而原厂 U-Boot 这条启动路径的 heap 只有约 8.25 MiB，大包在这里根本分配不出来。

解决方式是把启动和系统拆开：内核配一个很小的 initramfs，启动后挂载 NAND 上的 SquashFS，再把 Plugin 的 UBIFS 作为 overlay。启动 FIT 回到大约 5 MiB 这个量级，完整用户空间放在独立 rootfs。

同时还要修正 FIT 的描述、解密后的临时地址、内核解压地址、FDT、initrd 的摆放和厂商版本信息。看到 `Loading Kernel Image ... OK` 只能说明 U-Boot 搬完了某一段数据，不能拿这行当成 Linux 已经启动的证据。

## 刷之前先证明真的能恢复

我一开始觉得“两份 U-Boot 不动，A 坏了从 U-Boot 重刷”应该就够了。方向没错，但前提是自己真的清楚引导程序在哪、头在哪、擦除到底擦哪一段。

原厂 `/proc/mtd` 里面有 `whole flash`、`kernel1`、`rootfs1` 等各种视图，它们存在重叠，直接把大小相加肯定不对。厂商升级工具的整槽擦除范围也不能原封不动照搬，因为可能包含槽里的 U-Boot。

这次先从 RAM 系统读出静止的 128 MiB NAND ECC 数据，Mac 和 Linux 各存一份。整个备份又分成 16 个 8 MiB 块，通过 TFTP 送进 RAM，跟设备读回的数据逐字节比。

但“读出来了”还不是“能写回”。所以后面真的在计划扩容的区域写入新 UBI，挂载、写入随机文件、卸载再挂载确认内容，然后用备份把原来的 B 系统载荷和 Plugin 恢复回去，再比较字节。做完这一轮才继续正式安装。

写入顺序也有讲究：先载荷，最后提交能被引导程序选中的版本头。每一块传完检查，写完再读回检查。两份 U-Boot 的可执行字节单独核对。

这里要说准确一点：为了自动启动，早期曾调整过环境里的三项设置。所以是保留了两份 U-Boot 和早期引导的可执行代码，不是整个历史过程中 bootloader 所在分区一个字节都没碰过。

## B 系统可以不要，B 的线索不能全删

OpenClash 能跑之后，我就开始嫌存储小。原厂还有个 30 MiB 的 Plugin 分区，那就拿来保存配置。后面又觉得 B 系统既然不用，不如一起并进去。

最开始按 `0x3680000` 作为新 Plugin 起点去算，可以得到 73.5 MiB。看着很合理，前面的 B U-Boot 也还在。

但是继续跟 U-Boot 之前的那层 loader，就发现这事不能这么干。它要沿着版本头、内核定位标记去找 U-Boot。把 B 后面的信息全抹掉，某些 A 头损坏的情况下，即使 B 的 U-Boot 字节还在，loader 也未必找得到。

最后给 B 留了 256 KiB，放救援定位标记和版本头：

```text
0x3500000 .. 0x3680000   B U-Boot
0x3680000 .. 0x36c0000   B 救援定位与版本头
0x36c0000 .. 0x8000000   Plugin，73.25 MiB
```

真实启动时能看到新的 B 救援头。A 的头或定位信息损坏后能否找到 B U-Boot，用原始早期代码做了执行仿真；没有为了测试再把真机的 A 头故意砸坏。

另外，保留 B U-Boot 不等于保留了第二套系统。现在 B 已经没有完整 Linux，也不能说 A 内核随便怎么挂都会自动切 B 正常上网。

## 核心放 Flash，运行放 RAM

最后一个坑是更新。OpenClash 的小闪存模式会把核心放到 `/tmp`，运行没问题，但是在网页上更新完，断电之后更新就没了。

于是把核心的存储和运行分开：Plugin 保存压缩核心，开机解压到 RAM。rootfs 里还有一份已知可用的原始核心兜底。更新前先用新核心检查当前配置，再写入新归档、提交 `current` 指针。

最开始还在 Plugin 保留了“当前 + 上一版”，加上 rootfs 里的原始版本，回退是挺从容，就是两个压缩核心吃掉约 40 MiB，刚扩出来的空间又快没了。

我想了一下，rootfs 都有兜底了，Plugin 还留两份干嘛？

现在改成 Plugin 只留当前版本。更新过程中先保留旧版，等新版完整校验和提交成功再删；中断留下的多余归档会在后续成功恢复时清理。Plugin 当前核心坏了就退回 rootfs，不再保留一串历史版本。

这部分没有只跑几个模拟脚本就结束：实际通过 OpenClash 的更新脚本切到 v1.19.31，再更新回 v1.19.32，然后普通重启，确认运行版本、单份归档和代理请求都正常。改完后 `df` 剩余约 37.2 MiB。注意这是闪存可用空间，不是运行内存。

MetaCubeXD 则是网页文件，更新写进 overlay 后可以跨重启保留；它和替换整个 OpenClash 插件不是同一件事。整个插件升级会不会覆盖定制脚本，还需要按具体版本再看。

## 最后

现在这台机器已经能不靠串口辅助，正常上电进入 OpenWrt。三口收发、WAN/LAN、双频无线、配置保留、OpenClash 和核心更新都实际走过。原始双核心方案做过真正断电重上电，后续单核心调整又做了普通重启验证。

当然，“这些功能跑通了”和“已经跑了半年完全没问题”还是两件事。长期稳定性、极限吞吐、完整 IPv6 和正式的通用升级流程，还不能从这两天的测试里变出来。

最有意思的是，这次让我明显感觉到 AI 能把逆向、改驱动、构建、写测试这些事情接起来，但它依然不能替我插网线，不能替我确认天线到底在不在，更不能拿一次 QEMU 启动成功当成真机验收。

从“不想拆，最好一次成功”，一路做到焊串口、临时写 USB 串口桥、追 DMA、改分区，最后终于是台能用的路由器了。

代码在 [GaoYuCan/sr7100-openwrt](https://github.com/GaoYuCan/sr7100-openwrt)，里面保留了来源和具体边界。自己的校准、微码和备份要自己准备，别拿一台机器上的镜像直接往另一台上怼。

酣畅淋漓。
