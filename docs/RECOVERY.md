# SR7100 分区与恢复边界

本文描述已验证样机的最终布局。地址都是 NAND 的 ECC 数据区偏移，不包含 OOB。原厂 `/proc/mtd` 存在整片、kernel、rootfs 等重叠视图，不能把各项大小相加当成物理容量。

## 物理范围

| 起点 | 终点，不含 | 用途 |
| --- | --- | --- |
| `0x00000000` | `0x00800000` | 早期引导、环境、校准和原厂配置 |
| `0x00800000` | `0x00980000` | A U-Boot，保留可执行代码 |
| `0x00980000` | `0x00f80000` | A 内核启动载荷，6 MiB |
| `0x00f80000` | `0x033c0000` | A 只读 SquashFS rootfs，36.25 MiB |
| `0x033c0000` | `0x03400000` | A 元数据区，版本头位于 `0x033e0000` |
| `0x03400000` | `0x03500000` | 保留间隔 |
| `0x03500000` | `0x03680000` | B U-Boot，保留可执行代码 |
| `0x03680000` | `0x036c0000` | B 救援定位标记与版本头，256 KiB |
| `0x036c0000` | `0x08000000` | Plugin，73.25 MiB |

两份 U-Boot 可执行区在安装前后哈希相同。最初解决自动启动时，环境块 `0x80000..0xa0000` 中曾调整 `bootcmd`、`versioninfo`、`initrd_high`；因此准确表述是“保留引导可执行代码”，不是“整个 bootloader 分区从未改变”。后续 Plugin 扩容与核心存储调整没有再改环境。

## 为什么还留 B 元数据

U-Boot 之前的 loader 会根据版本头和内核定位标记寻找对应的 U-Boot。只保留 B 的 U-Boot 字节、把后面所有东西直接并入 Plugin，会破坏特定 A 故障下寻找 B 的路径。

最终保留 B locator `0x3680000`、B header `0x36a0000`，Plugin 从 `0x36c0000` 开始。真实启动日志已确认识别这个救援头；A 头/定位标记损坏后到达 B U-Boot 的分支以原始早期代码执行仿真验证。没有故意损坏真机 A 头，也没有验证任意 Linux 卡死都自动切 B。

## 原厂载荷格式要点

观察到的定位标记为小端四个字：`33333333 cccccccc 88888888 dddddddd`；版本 magic 位于 512 字节头的 `0xf4`，为 `33333333 66666666 99999999 cccccccc`。两个 CRC 分别位于 `0xa4` 和 `0x1fc`，覆盖各自之前的字节。

内核载荷在本机原厂启动路径使用 AES-ECB 包装。FIT 本身还需要正确的配置 description、每个组件的 SHA-256，以及不重叠的 U-Boot 临时区、解压地址、FDT 和 initrd 窗口。密钥和设备完整头从自己的引导程序及备份确认，仓库不捆绑引导镜像或密钥。

内核 FIT 模板使用 `0x8b000000` 作为内核 load/entry，FDT 使用 `0x87000000`，ramdisk 不指定固定 load。不要把 E2631/ZX279128S 的 legacy uImage 地址照搬到本机。

## 本次恢复验证做了什么

1. 从 RAM 系统读取静止 NAND，未挂载可写 UBI；128 MiB ECC 数据区连续两次读取哈希一致。
2. Mac、独立 Linux 主机各存一份，核对哈希。
3. 全备份按 16 个 8 MiB 块通过 TFTP 送入 RAM，与 NAND 读回数据逐字节比较。
4. 在扩容区域实际写入新布局，挂载 UBIFS，写入 8 MiB 随机文件，卸载重挂后校验。
5. 回到 U-Boot，把 B 系统载荷和原 Plugin 从备份写回，逐字节比较；保护区保持不变。
6. 正式安装按 B 救援元数据、Plugin、A boot/rootfs、A 版本头的顺序执行；版本头最后提交。

这台样机当时没有坏块。写入按原厂 `kernel1`、`kernel2`、`Plugin` 边界分块，每块做传输 CRC、ECC 写入、读回 CRC 与字节比较。没有验证出现新坏块后的自动重映射，也不把这组流程直接推广到其他 NAND 型号。

Linux 与 U-Boot 的 OOB 约定不同。这里的备份不是“含 OOB 的 raw dump”，恢复也不能使用 raw/OOB 写法。必须理解自己使用的命令究竟在写哪一种格式。

## Linux 侧的写保护

RAM DT 配合只读 SFC 策略拒绝 NAND 编程/擦除。安装 DT 仅允许 `0x36c0000..0x8000000` 的阵列修改；判断位于 SPI NAND 操作层，不仅依赖分区 `read-only` 标志。测试逐页覆盖 program-execute、block-erase 和寄存器操作范围。

`init-installed` 只附着已准备好的 UBI，不会发现空卷后自动格式化。标记错误、挂载失败或布局异常会进入诊断 shell，保留数据。

## 使用者需要准备

独立管理主机、串口、同机原始校准、双份完整备份、原厂 U-Boot 命令与权限、RAM 镜像验收、针对当前 NAND 的写回恢复实测，以及明确的刷写范围。串口用来恢复时不能依赖待修路由器自身的 Wi-Fi。示例 ESP32 接线见对应目录说明。

`tools/flash-plan.py` 只输出离线布局，不会发送任何设备命令。对其他机器，应先重建自己的证据和恢复材料，再开发受限写入工具。
